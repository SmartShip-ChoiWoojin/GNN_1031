# 처음부터 만든다면 — 구현 순서 가이드

백지 상태에서 이 프로젝트(FE 메쉬 정상/비정상 분류 GNN)를 다시 만든다면 어떤 순서로
무엇을 보고 짜야 하는지를 적은 문서다. 이미 짜여 있는 코드의 설명은 [README.md](../README.md)
와 각 소스의 docstring 에 있고, 여기서는 **순서와 판단 근거**만 다룬다.

> **같이 읽을 것**: [코드로 배우는 파이썬](코드로_배우는_파이썬.md) — 이 문서가
> "어떤 순서로 짜는가"라면, 그쪽은 "그 코드를 실제로 어떻게 쓰는가"(클래스·함수 문법,
> 라이브러리 사용법, 왜 그 자료구조를 골랐는지)를 다룬다.

핵심 원칙 하나만 먼저 말하면 이렇다.

> **아래에서 위로 쌓고, 각 층이 맞는지 확인한 다음에 다음 층으로 올라간다.**
> 모델부터 짜면 안 된다. 파싱이 틀려 있으면 모델이 아무리 좋아도 틀린 답이 나오는데,
> 그 사실을 알아챌 방법이 없다.

전체 층 구조는 이렇다. 아래가 먼저다.

```
    7. 화면 (app.py)
    6. 설명력 (explain.py)          <- 어느 요소가 문제인지
    5. 학습·평가 (train.py)
    4. 모델 (models.py)
    3. 그래프 변환 (graph_elem.py)   <- 여기부터 GNN 영역
    2. 피처 (features.py)
    1. 표현 (meshrep.py)            <- 연결 관계
    0. 파싱 (bdf_io.py, labels.py)  <- 여기가 틀리면 전부 틀린다
```

---

## 0단계. 코드를 짜기 전에 — 데이터부터 본다

**가장 많이 건너뛰고, 가장 비싸게 대가를 치르는 단계다.** 에디터로 파일을 직접 열어본다.

### 봐야 할 것

| 무엇을 | 왜 |
|---|---|
| `.bdf` 파일을 **텍스트 에디터로 직접** 열기 | 고정폭인가 콤마 구분인가, 카드 종류가 몇 가지인가 |
| `.json` 파일 열기 | 키가 문자열인가 숫자인가, 값이 true/false 인가 |
| 라벨 엑셀 열기 | 헤더가 몇 행째인가, 컬럼 이름이 정확히 무엇인가 |
| 파일 개수 세기 | bdf 와 json 이 짝이 맞는가, 라벨 행 수와 맞는가 |

### 이 프로젝트에서 실제로 확인한 것

- `.bdf` 는 **콤마 구분**이고 카드는 `GRID`, `CQUAD4`, `CTRIA3`, `CBAR`, `CBEAM` 5종뿐이다
- `PID`(물성 번호)는 전부 1이라 피처로 쓸 값이 없다
- 라벨 엑셀은 **위쪽 12행이 통계 요약**이고 실제 표 헤더는 13행째다
- 라벨 컬럼은 `분류 결과(숫자)` 가 0/1/2, `확실(0)/애매(1)` 가 따로 있다

마지막 두 개는 파일을 안 열어봤으면 못 찾는다. `pd.read_excel(path)` 만 했으면 헤더를
잘못 잡고 조용히 틀린 표를 얻는다.

### 산출물: **가정 목록**

여기서 확인한 것을 "가정"으로 적어두고, 다음 단계에서 **코드에 어서션으로 박는다.**
나중에 데이터가 바뀌면 조용히 틀리는 대신 바로 터지게 하려는 것이다.

## 1단계. 파싱 — 밑바닥을 먼저 굳힌다

**파일**: `bdf_io.py`, `labels.py`, `paths.py`, `data_index.py`

### 짜는 순서

1. **`paths.py` 부터** — 경로 상수를 한 곳에 모은다. 3줄짜리 파일이지만 먼저 만든다.
   다른 파일에 경로를 하드코딩하면 나중에 데이터 폴더를 바꿀 때 전부 뒤져야 한다.
   실제로 이 프로젝트는 폴더를 한 번(`fe model 1D 0706` → `SN2592_FWD_Clean`),
   라벨 엑셀을 한 번(`0721` → `0918`) 갈아끼웠다. 한 줄씩만 고쳤다.

2. **`bdf_io.py`** — `.bdf` 와 `.json` 을 읽어 좌표/요소/외부연결 정보를 돌려준다.
   0단계에서 적은 가정을 **`assert` 로 박는다.** 예: 카드 종류가 5종뿐이라는 가정.

3. **`labels.py`** — 엑셀에서 `name / cls / ambig / trainable` 을 만든다.
   헤더 행 위치를 하드코딩하지 말고 **스캔해서 찾는다**(`'이름'` 과 `'분류'` 가 같이
   있는 행). 엑셀은 사람이 편집하는 파일이라 행이 밀린다.

4. **`data_index.py`** — "어떤 모델을 학습에 쓸지"를 한 곳에서 정한다.
   규칙: **확실(ambig=0) 이고 분류어려움(cls=2)이 아닌 것만.**

### 반드시 같이 만들 것: 검증 스크립트

`check_parsing.py` 를 **이 시점에** 만든다. 전 파일을 파싱해 보고 이상한 것이 있으면
출력한다. 모델을 다 만든 뒤에 "왜 성능이 안 나오지" 하며 돌아오는 것보다 백 배 싸다.

여기에 **회귀 테스트** 하나를 박아둔다. 특정 파일 하나의 파싱 결과를 숫자로 고정한다.

```
SN2592_FWD_Clean_0001 : 절점 55 / CQUAD4 42 / CTRIA3 1 / CBAR 29 / CBEAM 9
```

이후 파싱 코드를 고칠 때마다 이 숫자가 그대로인지 본다. 바뀌면 뭔가 깨진 것이다.

### 완료 기준

- [ ] 전 파일이 예외 없이 파싱된다
- [ ] bdf/json 짝이 맞지 않는 파일 목록을 출력할 수 있다
- [ ] 라벨 분포(정상/비정상/분류어려움 × 확실/애매)를 출력할 수 있다
- [ ] 회귀 테스트 1건이 통과한다

### 함정

> **엑셀 셀을 숫자로 못 읽어도 `pd.to_numeric(..., errors="coerce")` 는 에러를 내지 않는다.**
> 조용히 `NaN` 이 되고, 그게 "애매"로 처리되어 학습 대상에서 빠진다. 학습 대상 수를
> **항상 출력**해서 눈으로 확인해야 한다. 이 프로젝트에서는 3223개가 기준값이다.

## 2단계. 표현 — 연결 관계를 만든다

**파일**: `meshrep.py`

파싱 결과는 "절점 목록"과 "요소 목록"일 뿐이라, **어느 요소가 어느 요소와 붙어 있는지**
모른다. 그래프를 만들려면 그 관계가 필요하다.

### 만들어야 할 것

| 자료구조 | 내용 | 나중에 쓰이는 곳 |
|---|---|---|
| `edge_shells` | 변 → 그 변을 공유하는 쉘 목록 | 그래프의 "변 공유" 엣지 |
| `node_shells` | 절점 → 그 절점을 쓰는 쉘 목록 | "꼭짓점 공유" 엣지 |
| `edge_lines` | 변 → 그 위에 놓인 1D 요소 | "1D-쉘" 엣지 |
| `node_lines` | 절점 → 거기 붙은 1D 요소 | "1D-1D" 엣지 |

`edge_shells` 하나만 있어도 많은 것을 알 수 있다.

- 공유하는 쉘이 **1개** → 경계변(자유변)
- **2개** → 정상
- **3개 이상** → 비정상 연결(non-manifold). 이것 자체가 불량 신호다

### 완료 기준

- [ ] 메쉬 하나에 대해 경계변/정상/비정상 변 개수를 셀 수 있다
- [ ] 요소마다 이웃 요소 목록을 뽑을 수 있다

## 3단계. 피처 — "이상함"을 숫자로

**파일**: `features.py`

### 설계 원칙 두 가지

**① 좌표의 절대값을 쓰지 않는다.**

이 패치들은 한 척의 배에서 잘라낸 조각이라 위치가 제각각이다. 좌표를 그대로 넣으면
모델이 *"x 가 24만 근처면 비정상이 많더라"* 같은 규칙을 외운다. 학습 데이터에서는
맞지만 새 배에서는 전혀 쓸모없다.

대신 **각도와 비율**만 쓴다. 내각, aspect ratio, skew, warp, taper, 정규화 야코비안,
이면각 — 전부 평행이동·회전·크기에 영향받지 않는 양이다.

**② 순수 함수로 짠다.**

`features.py` 는 numpy 배열을 받아 숫자를 돌려주는 함수만 둔다. 클래스도, 전역 상태도
없다. 그래야 단독으로 시험해볼 수 있다.

### 같이 정해둘 것: 규칙 기반 판정

`is_bad_shell()` — 최소내각 < 30도 또는 최대내각 > 150도면 불량.

이건 모델이 아니라 **사람이 아는 규칙**이다. 나중에 두 가지로 쓰인다.

- 모델이 지목한 요소가 이 규칙과 겹치는지 보는 기준
- *"규칙으로 될 걸 왜 GNN 으로 하냐"* 는 질문에 답하는 근거

### 완료 기준

- [ ] 쉘 하나의 품질 지표를 손으로 계산해 검산했다
- [ ] 삼각형/사각형 양쪽에서 동작한다
- [ ] 좌표를 전부 +1000 평행이동해도 값이 그대로다

## 4단계. ★ 기준선 먼저 — GNN 을 짜기 전에

**파일**: `baseline.py`

**이 단계를 건너뛰면 나중에 자기 모델이 좋은지 나쁜지 말할 수 없게 된다.**

### 무엇을 하는가

메쉬 한 개를 **숫자 몇십 개로 요약**한다(요소 개수, 삼각형 비율, 최소 내각, 불량 요소
개수, 자유변 개수 등 37개). 그리고 평범한 머신러닝(HistGradientBoosting)에 넣는다.

그래프도, 딥러닝도 아니다. 반나절이면 짠다.

### 왜 먼저 하는가

GNN 이 AUC 0.98 을 냈다고 하자. 좋은 숫자인가? **모른다.**
집계 피처 + GBM 이 0.956 을 낸다면, GNN 의 기여는 0.024 뿐이다.

| | AUC | ACC | F1 |
|---|---|---|---|
| 기준선 (집계 37개 + GBM) | 0.9560 | 0.8895 | 0.8613 |
| GNN (요소 그래프 + GATv2) | **0.9823** | **0.9364** | **0.9208** |
| 차이 | +0.0263 | +0.0469 | +0.0595 |

이 표가 있어야 *"GNN 을 왜 쓰냐"* 는 질문에 답할 수 있다. 그리고 만약 GNN 이 기준선을
못 넘으면 **그래프 설계가 잘못된 것**이므로 되돌아가야 한다는 신호가 된다.

### 완료 기준

- [ ] 기준선 수치를 상수로 박아뒀다 (`train.py` 의 `BASELINE`)
- [ ] 이후 모든 모델 결과를 이 숫자와 나란히 출력한다

## 5단계. 그래프 설계 — 가장 중요한 선택

**파일**: `graph_base.py`, `graph_elem.py`, `graph_node.py`, `graphs.py`

### 핵심 질문: 무엇을 노드로 둘 것인가

두 가지 선택지가 있고, **둘 다 만들어 비교하는 것이 정답이다.**

| | 절점 기반 | **요소 기반** |
|---|---|---|
| 노드 | GRID 절점 | 쉘/1D 요소 |
| 엣지 | 요소의 변 | 요소 사이의 인접 관계 |
| 피처 | 절점 주변 통계 | 요소 자체의 품질(각도, aspect...) |
| 장점 | 메쉬와 모양이 같아 직관적 | **판정 대상에 직접 피처가 붙는다** |
| 지목 | 절점 → 요소로 환산 필요 | **요소를 바로 지목** |

실측 결과 요소 기반이 나았다(AUC 0.9602 vs 0.9569). 그런데 **숫자 차이보다 중요한 것은
"어느 요소가 문제인지" 를 바로 말할 수 있다는 점**이었다. 목적이 분류만이 아니라
지목이었기 때문이다.

### 엣지를 한 종류로 두지 않는다

관계마다 의미가 다르므로 **종류를 구분해서 알려준다.**

| 번호 | 관계 | 의미 |
|---|---|---|
| 0 | 쉘-쉘, 변 공유 | 가장 강한 인접 |
| 1 | 쉘-쉘, 꼭짓점만 공유 | 약한 인접 |
| 2 | 1D-쉘 | 보강재가 그 변에 놓임 |
| 3 | 1D-1D | 보강재끼리 이어짐 |

엣지 피처에 관계 종류를 one-hot 으로 넣고, 거기에 이면각·길이비 같은 기하량을 더한다.

### 타입별로 없는 피처는 마스킹한다

1D 요소에는 "면적"이 없다. 그냥 0 을 넣으면 안 된다. 정규화할 때 그 0 들이 쉘의
평균을 끌어내린다. **유효성 마스크(`x_valid`)** 를 같이 만들어, 해당 없는 칸은
통계에서 빼고 변환 후 정확히 0 으로 둔다.

### 완료 기준

- [ ] 메쉬 하나를 그래프로 바꾸고 노드/엣지 수를 손으로 검산했다
- [ ] 관계 4종의 개수가 각각 말이 되는지 확인했다
- [ ] 그래프를 3D 로 그려서 눈으로 봤다 (이 단계에서 버그가 제일 잘 보인다)

## 6단계. 정규화와 데이터셋 — 누출을 막는 층

**파일**: `featspec.py`, `dataset.py`

### 여기가 조용히 틀리기 가장 쉬운 곳이다

**누출(leakage)**: 평가에 쓸 데이터의 정보가 학습에 새어 들어가는 것. 성능이 실제보다
좋게 나오고, 현장에 배포하면 무너진다.

지켜야 할 규칙:

> **정규화 통계(평균·표준편차)는 학습 몫에서만 계산한다.**

| 방식 | 문제 |
|---|---|
| 그래프마다 따로 정규화 | 메쉬 간 비교가 불가능해진다. 모든 메쉬의 최악 요소가 똑같이 -3 이 된다 |
| 전체 데이터로 한 번에 정규화 | **누출.** 평가 데이터의 분포를 학습이 미리 안다 |
| **학습 몫에서만 적합** | 올바름 |

### 척도 선택도 데이터를 보고 정한다

처음에는 중앙값/MAD 를 썼다. 이상치에 강해서다. 그런데 **이면각처럼 0도 아니면 90도인
양봉 분포에서는 MAD 가 0 에 가까워져** 값이 전부 폭발했다. 실측으로 `s_ny` 의 46%,
`dihedral` 의 42%가 클리핑 한계(±10)에 걸렸다.

**윈저화 표준편차**(0.5~99.5 백분위로 자른 뒤 std)로 바꾸니 클리핑이 0.007% 로 떨어졌다.

> 교훈: 정규화 후 **클리핑에 걸리는 비율을 반드시 출력해 본다.** 안 보면 모른다.

### 캐시를 만든다면

4000개를 매번 파싱·변환하면 느리니 캐시한다. 단:

> **캐시에는 그래프만 담는다. 라벨은 담지 않는다.**

그래프는 `.bdf`/`.json` 에서만 나오므로 라벨과 무관하다. 라벨까지 캐시에 넣으면,
라벨 엑셀을 갈아끼워도 **옛 라벨이 조용히 그대로 쓰인다.** 이 프로젝트에서 실제로
겪었다(라벨 340개가 바뀐 엑셀로 교체했는데 캐시 때문에 반영이 안 됐다).

### 완료 기준

- [ ] 정규화 후 값의 범위와 클리핑 비율을 출력해 확인했다
- [ ] 정규화 통계가 학습 몫에서만 적합되는지 코드로 확인했다
- [ ] 캐시 키에 무엇이 반영되는지 분명히 알고 있다

## 7단계. 모델

**파일**: `models.py`

### 순서

1. **가장 단순한 것부터.** 메시지 전달 2~3층 + 평균 풀링 + 선형 분류기.
   먼저 "돌아가는가"를 확인하고, 성능은 그다음이다.
2. 엣지 피처를 쓸 수 있는 층을 고른다(`GINEConv`, `GATv2Conv`). 엣지 종류를
   구분해 넣었으니 그걸 쓰지 못하는 층은 의미가 없다.
3. **읽기(readout)에 어텐션 풀링을 넣는다.** 이게 설명력의 핵심이다. 요소마다
   가중치를 내주므로 "어느 요소를 보고 판단했는지"가 그대로 나온다. 평균 풀링만
   쓰면 분류는 되지만 지목을 할 수 없다.
4. 읽기는 **평균 + 최대 + 어텐션을 이어 붙인다.** 서로 다른 성질을 본다.

### 타입이 섞여 있으면 인코더를 나눌지 검토한다

쉘과 1D 는 성질이 다른데 같은 인코더를 쓰면, 모델이 "타입" 자체를 지름길로 쓸 수 있다.
분리해 본 결과:

| | 분류 성능 | 불량 요소 지목 AUC | top-1 적중 |
|---|---|---|---|
| 공유 | 0.9647 | 0.605 | 0.300 |
| **분리** | 0.9586 | **0.816** | **0.496** |

**분류 성능은 차이가 없는데 지목 품질이 크게 올랐다.** 목적이 지목이라면 분리가 맞다.
이런 건 분류 정확도만 보고 있으면 절대 발견하지 못한다.

## 8단계. 학습과 평가 프로토콜

**파일**: `train.py`

### 평가 설계를 먼저 정한다 — 코드보다 먼저

**세 몫으로 나눈다.**

| 몫 | 역할 |
|---|---|
| 학습분 | 가중치를 실제로 업데이트 |
| 검증분 | 언제 멈출지 결정, 확률 보정 |
| 평가분 | **한 번도 안 본다.** 최종 점수 전용 |

검증분과 평가분을 같이 쓰면 안 된다. "언제 멈출지"를 평가 데이터로 정하면 그 점수는
더 이상 정직하지 않다.

### 조기종료가 필요한 이유 (실측)

| | epoch 20 | epoch 80 |
|---|---|---|
| loss (학습분) | 0.0768 | **0.0137** ↓ 계속 좋아짐 |
| 검증 AUC | 0.9869 | **0.9859** ↑ 더는 안 좋아짐 |

`loss` 는 모델이 직접 깎는 값이라 **계속 내려가는 게 당연하다.** 멈출 시점을 알려주지
못한다. 검증분만이 "실력이 늘고 있는가"를 알려준다.

### "학습 데이터는 100% 맞아야 하지 않나" — 아니다 (실측)

| | 학습분 AUC | 학습분 ACC | 안 본 데이터 AUC | 안 본 데이터 ACC |
|---|---|---|---|---|
| 정상 (dropout 0.3 + 조기종료) | 0.9968 | 0.9509 | **0.9838** | **0.9401** |
| 끝까지 맞추기 (dropout 0, 200 epoch) | **1.0000** | **0.9987** | 0.9734 | 0.9333 |

학습 데이터 AUC 를 1.0 까지 끌어올리면 **안 본 데이터에서는 오히려 나빠진다**
(오답 193 → 215개). 학습셋 100% 는 목표가 아니라 경계해야 할 신호다.

### fold 간 확률 스케일을 맞춘다

5-fold 를 쓰면 fold 마다 확률 스케일이 달라서, 그냥 모아 계산하면 종합 AUC 가
떨어진다(0.9707 → 0.9522). **Platt 보정**(검증분으로 적합하는 1차 변환)을 넣으면
단조 변환이라 fold 별 AUC 는 그대로 두고 종합만 회복된다(0.9662).

### 배포용 모델은 따로 만든다 ★

**5-fold 는 성능을 재는 기법이지 배포 방식이 아니다.**

이 프로젝트는 측정용 fold 모델 5개를 그대로 배포했다가 사고가 났다. "이 메쉬를 몇 번
모델이 판정할지"를 실행할 때마다 다시 계산했는데, 그 계산이 **학습 대상 목록의 순서**에
의존했다. 목록이 하나만 어긋나도 담당 모델이 바뀌어서, 같은 메쉬가 PC 마다 다른 답을
냈다(0.44 정상 vs 0.88 비정상).

| 목록에서 빠진 수 | 담당 모델이 바뀌는 비율 |
|---|---|
| 1개 | 38% |
| 3개 | 63% |
| 10개 | 68% |

**올바른 방식**: 성능은 5-fold 로 재고, 배포는 **전체 데이터로 학습한 모델 하나**로 한다.
그러면 파일 이름에도, 목록 순서에도, 캐시 상태에도 결과가 의존하지 않는다.

## 9단계. 설명력 — "어느 요소가 문제인가"

**파일**: `explain.py`

어텐션 가중치 `alpha` 가 곧 요소별 기여도다. 그래프 안에서 합이 1 이므로 **노드 수를
곱해 "평균 대비 몇 배"** 로 바꿔 보면 크기가 다른 메쉬끼리 비교할 수 있다.

### 검증을 반드시 한다

지목이 그럴듯해 보이는 것과 실제로 맞는 것은 다르다. **규칙 기반 불량 요소를 정답으로
두고** 지목 성능을 측정한다(bad-element AUC, top-1/top-3 적중률). 7단계의 인코더 분리
판단이 이 수치로 이루어졌다.

## 10단계. 화면

**파일**: `app.py`

### 원칙

- **초기 화면은 형상만 보여준다.** 중요도 색칠은 꺼진 상태로 시작한다. 처음부터
  알록달록하면 메쉬 모양 자체가 안 보인다
- 색은 **한 계열**만 쓴다. 무지개색은 순서를 오해하게 만든다
- **학습에 쓴 메쉬와 안 쓴 메쉬를 화면에서 구분**한다. 안 그러면 지금 보는 값이
  정직한 평가인지 알 수 없다
- 한 화면에 **여러 모델의 값을 섞지 않는다.** 섞으면 "목록은 FP 라는데 화면은
  정상이라고 나온다" 같은 모순이 생긴다

### 미리 계산해 둔다

오분류 목록처럼 전체를 훑어야 하는 기능은, 배포 모델이 고정이므로 **결과도 고정**이다.
배포 전에 한 번 계산해 `predictions.csv` 로 같이 넣는다. 앱이 켜질 때마다 수천 번
추론하면 못 쓴다.

---

## 11단계. 배포

```bash
# 1) 배포 모델 (전체 데이터, fold 없음) + 예측 캐시까지 한 번에
python scripts/train_deploy.py

# 2) 성능 측정 (5-fold) — 배포하지 않는다. 보고용 숫자를 얻는 것이 목적
python scripts/run_validation.py --baseline --compare

# 3) 화면
streamlit run src/app.py
```

`train_deploy.py` 는 두 단계로 돈다. 먼저 15%를 검증셋으로 떼고 학습해 **최적 epoch 와
확률 보정 계수**를 구하고(`runs/train/calib`), 그다음 검증셋 없이 전 데이터로 그 epoch
만큼만 다시 학습한다(`runs/train/deploy`). epoch 수를 사람이 정해 박아 넣지 않기 위한
구조다.

### 배포본에 넣을 것

- `src/` 전체, `runs/train/deploy/`(모델 + predictions.csv), 데이터 폴더, 라벨 엑셀
- **실행 폴더는 하나만 넣는다.** 여러 개를 넣으면 사용자가 옛 라벨로 학습된 모델을
  고를 수 있고, 또 "왜 결과가 다르냐"가 반복된다

### 사내 배포 시 주의

- 라벨 엑셀에 **DRM 암호**가 걸린다 → `fasoo_drm.setting_fasoo()` 를 진입점에서 호출
- 한글 Windows 콘솔은 **cp949** 라 `—`(em dash) 같은 문자를 출력하면 **프로그램이 죽는다.**
  `print` 문에는 ASCII 와 한글만 쓴다
- 배치 파일에 한글을 쓰지 않는다. 괄호도 `if` 블록 안에서 파서를 깨뜨린다

## 부록. 실제로 밟은 지뢰 모음

같은 걸 또 밟지 않도록 모아둔다. 전부 **에러 없이 조용히 틀리는** 종류다.

| 지뢰 | 증상 | 교훈 |
|---|---|---|
| 그래프별 정규화 | 메쉬 간 비교 불가 | 정규화 범위를 의식적으로 정한다 |
| MAD 척도 | 양봉 분포에서 값 폭발, 46% 클리핑 | 정규화 후 분포를 출력해 본다 |
| 타입별 결측을 0 으로 | 1D 의 0 이 쉘 통계를 오염 | 유효성 마스크를 쓴다 |
| fold 간 스케일 차이 | 종합 AUC 만 낮게 나옴 | Platt 보정 |
| 캐시에 라벨 포함 | 엑셀 교체가 반영 안 됨 | 캐시에는 불변인 것만 담는다 |
| fold 배정 재계산 | PC 마다 다른 예측 | 측정과 배포를 분리한다 |
| 파일명으로 식별 | 이름 바꿔 올리면 다른 경로 | 내용으로 식별한다 |
| `errors="coerce"` | 라벨이 조용히 "애매"로 바뀜 | 개수를 출력해 확인한다 |
| em dash in print | 사내 PC 에서만 즉시 종료 | 콘솔 인코딩을 고려한다 |

## 부록. 파일을 짜는 순서 (.py 단위)

순서의 근거는 취향이 아니라 **import 의존 관계**다. 실제 의존 그래프를 뽑으면 순환 없이
7층으로 갈라진다.

```
0층  paths, bdf_io, labels, features, featspec, graph_base, models, fasoo_drm
1층  meshrep(<-bdf_io,features)  data_index(<-bdf_io,labels,paths)
2층  graph_elem, graph_node(<-featspec,features,graph_base,meshrep)  baseline  check_parsing
3층  graphs(<-graph_elem,graph_node)
4층  dataset(<-graphs,featspec,data_index)
5층  train, explain(<-dataset,models)
6층  app, predict_all, compare
```

의존 관계는 "이것보다 늦게"만 정해준다. 그 안에서 실제로 어떤 순서로 쓰는지, 파일마다
언제 다음으로 넘어가도 되는지, 분량은 어느 정도인지는
**[코드로 배우는 파이썬 - 부록](코드로_배우는_파이썬.md#부록-파일을-짜는-순서-py-단위)**
에 표로 정리해 뒀다.

## 읽는 순서 요약

처음 보는 사람이 코드를 따라갈 때:

1. `paths.py` → `bdf_io.py` → `labels.py` → `data_index.py` (데이터가 들어오는 길)
2. `meshrep.py` → `features.py` (메쉬를 이해하는 층)
3. `graph_elem.py` (그래프로 바뀌는 지점 — **여기가 제일 중요하다**)
4. `featspec.py` → `dataset.py` (정규화와 배치)
5. `models.py` → `train.py` (학습)
6. `explain.py` → `app.py` (지목과 화면)

각 파일의 docstring 에 "왜 이렇게 했는지"를 적어뒀으니 같이 읽으면 된다.
