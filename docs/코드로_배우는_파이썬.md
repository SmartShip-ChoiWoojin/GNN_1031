# 코드로 배우는 파이썬 — 이 프로젝트의 문법과 설계

[처음부터 만든다면](처음부터_만든다면.md) 이 **"어떤 순서로 짜는가"** 를 다룬다면,
이 문서는 **"그 코드를 실제로 어떻게 쓰는가"** 를 다룬다. 이 프로젝트에 실제로 들어
있는 코드만 예시로 쓴다. 인터넷 예제가 아니라 눈앞의 코드로 문법을 익히는 것이 목적이다.

최종 목표는 **아무것도 안 보고 비슷한 것을 짤 수 있게 되는 것**이다. 그래서 각 절은

> 문법 → 이 프로젝트의 실제 코드 → **왜 다른 방법 대신 이걸 골랐는가** → 직접 해보기

순서로 되어 있다. 마지막 절에 "안 보고 짜기" 훈련 과정을 따로 뒀다.

---

## 1. 파일 한 개의 뼈대

파이썬 파일은 보통 이 순서로 쓴다. `bdf_io.py` 의 머리 부분이 교과서적이다.

```python
"""Nastran .bdf 벌크 데이터 + 절점 외부연결 .json 파서.

이 데이터셋(SN2592_FWD_Clean_*)은 형식이 매우 균일하다:
  - 카드는 GRID / CQUAD4 / CTRIA3 / CBAR / CBEAM 뿐
  ...
"""

from __future__ import annotations      # 1) 미래 문법 활성화 (항상 맨 위)

import json                             # 2) 표준 라이브러리
import os
from dataclasses import dataclass

import numpy as np                      # 3) 외부 라이브러리

SHELL_TYPES = ("CQUAD4", "CTRIA3")      # 4) 모듈 상수 (대문자)
```

### 각각이 왜 거기 있는가

**① `"""..."""` 모듈 docstring** — 파일 첫 줄의 문자열은 그냥 주석이 아니라
`bdf_io.__doc__` 로 꺼내 쓸 수 있는 **값**이다. `help(bdf_io)` 가 이걸 보여준다.
여기엔 "이 파일이 무엇을 하는가"뿐 아니라 **전제와 판단 근거**를 적는다. 위 예시가
"형식이 균일하다"는 관찰을 적어둔 덕에, 나중에 왜 파서가 이렇게 단순한지 알 수 있다.

**② `from __future__ import annotations`** — 타입 힌트를 문자열처럼 지연 평가한다.
이게 있어야 `dict[int, tuple[float, float, float]]` 같은 표기를 옛 파이썬에서도 쓸 수
있고, 아직 정의되지 않은 클래스 이름을 타입으로 쓸 수 있다. **반드시 파일 맨 위**
(docstring 바로 다음)에 와야 한다.

**③ import 를 세 묶음으로** — 표준 라이브러리 / 외부 패키지 / 내 모듈 순으로 띄어 쓴다.
강제는 아니지만 모두가 이렇게 하므로 따르면 읽기 쉽다.

**④ 상수는 대문자** — 파이썬에는 진짜 상수가 없어서 **대문자가 "바꾸지 마라"는 약속**이다.

### 직접 해보기
`src/features.py` 와 `src/models.py` 의 머리 부분을 열어 같은 구조인지 확인하라.

## 2. 함수 문법

### 기본형

```python
def _fields(line: str) -> list[str]:
    return [f.strip() for f in line.split(",")]
```

- `line: str` — **인자 타입 힌트**. 파이썬은 이걸 검사하지 않는다. 사람과 에디터를
  위한 것이다. 틀려도 실행은 된다(그래서 더 정직하게 써야 한다).
- `-> list[str]` — **반환 타입 힌트**.
- `_fields` — 이름 앞 `_` 는 **"이 모듈 안에서만 쓰는 내부 함수"** 라는 관례다.
  강제력은 없지만, `from bdf_io import *` 할 때 딸려 가지 않는다.

### 인자의 네 가지 형태

`models.py` 의 `mlp` 하나에 세 가지가 다 들어 있다.

```python
def mlp(*dims: int, dropout: float = 0.0) -> nn.Sequential:
    layers: list[nn.Module] = []
    for i in range(len(dims) - 1):
        layers.append(nn.Linear(dims[i], dims[i + 1]))
        ...
    return nn.Sequential(*layers)
```

| 형태 | 예 | 의미 |
|---|---|---|
| 위치 인자 | `def f(a)` | 순서대로 받는다 |
| 기본값 | `dropout: float = 0.0` | 안 주면 0.0 |
| `*args` | `*dims: int` | **개수 제한 없이** 받아 **튜플**로 묶는다 |
| `**kwargs` | `**opts` | 키워드 인자를 **딕셔너리**로 묶는다 |

`mlp(47, 128, 128, 1)` 처럼 층 크기를 몇 개든 줄 수 있는 건 `*dims` 덕이다.
그리고 `nn.Sequential(*layers)` 의 `*` 는 **반대 방향** — 리스트를 풀어서 개별 인자로
넘긴다. 같은 기호가 묶기/풀기 양쪽에 쓰인다.

`**opts` 는 `graphs.build` 에서 쓴다.

```python
def build(rep: MeshRep, kind: str, **opts) -> GraphArrays:
    return builder(kind)(rep, **opts)
```

호출부가 `graphs.build(rep, "elem", corner_edges=True, include_lines=True)` 라고 하면
`opts == {"corner_edges": True, "include_lines": True}` 가 되고, 그대로 다시 풀어서
전달한다. **중간 함수가 옵션 목록을 알 필요가 없어진다.**

### 여러 값 반환은 튜플이다

```python
coords, shells_raw, lines_raw = read_bdf(bdf_path)
```

파이썬은 "다중 반환"이 따로 있는 게 아니라 **튜플 하나를 반환하고 그걸 풀어 받는 것**이다.
`return a, b, c` 는 `return (a, b, c)` 와 같다.

> **언제 튜플 대신 dataclass 를 쓰나?** 반환값이 3개를 넘거나, 의미가 헷갈리기 시작하면
> 바꾼다. `read_bdf` 는 3개라 튜플로 두지만, 그 결과를 담는 `RawMesh` 는 5개 필드라
> dataclass 로 만들었다.

### 키워드 인자로 호출해 실수를 막는다

`train.py` 에서 실제로 쓴 방식이다.

```python
y_te, p_te, m, ckpt = train_one_fold(
    args=args, arrays=arrays, labels=labels, names=names,
    tr_idx=tr_idx, te_idx=te_idx, device=device, fold=fold,
)
```

`train_one_fold(args, arrays, labels, names, tr_idx, te_idx, ...)` 처럼 위치로 넘기면
`tr_idx` 와 `te_idx` 를 **바꿔 넣어도 에러가 안 난다.** 학습/평가 데이터가 뒤바뀌는데
조용히 돌아간다. 인자가 많고 같은 타입이면 **이름을 붙여 호출**하는 게 안전하다.

### 직접 해보기
`src/features.py` 에서 인자를 2개 이상 받는 함수를 찾아, 위치를 바꿔 넣어도 에러가
나지 않는 경우가 있는지 보라.

## 3. 자료구조 고르기

파이썬 기본 자료구조 네 가지를 이 프로젝트가 **각각 왜 골랐는지** 보자.

```python
SHELL_TYPES = ("CQUAD4", "CTRIA3")              # 튜플: 바뀌지 않는 목록
TYPE_INDEX = {t: i for i, t in enumerate(ELEM_TYPES)}   # 딕셔너리: 이름 -> 번호
Edge = frozenset                                 # 불변 집합: 무방향 절점쌍
self.edge_shells: dict[Edge, list[int]] = defaultdict(list)
```

| 자료구조 | 성질 | 이 프로젝트의 선택 이유 |
|---|---|---|
| `list` | 순서 있음, 변경 가능 | 요소 목록 — 순서가 곧 노드 번호 |
| `tuple` | 순서 있음, **변경 불가** | 상수 목록. 실수로 바꾸는 사고 방지 |
| `dict` | 키 → 값, 조회 빠름 | 절점 id → 좌표 |
| `set` | 중복 없음, 순서 없음 | 이미 만든 엣지인지 확인 |

### `Edge = frozenset` 이 왜 중요한가

변(edge)은 **절점 두 개**로 정해지는데 **순서가 없다.** 절점 3번과 7번을 잇는 변은
`(3, 7)` 이든 `(7, 3)` 이든 같은 변이다.

- `tuple` 로 두면 `(3,7) != (7,3)` 이라 같은 변이 둘로 센다 → **버그**
- `set` 으로 두면 순서는 없어지지만 **딕셔너리 키로 쓸 수 없다**(가변이라)
- `frozenset` 은 순서 없고 불변이라 **키로 쓸 수 있다** → 정답

```python
Edge = frozenset  # frozenset[int] — 무방향 절점쌍
```

이 한 줄이 "자료구조를 잘못 고르면 생기는 버그"를 통째로 막는다. `Edge` 라는 이름을
붙인 건 **의도를 드러내기 위해서**다. 코드에 `frozenset` 이라고 쓰여 있으면 왜
frozenset 인지 매번 생각해야 하지만, `Edge` 라고 쓰여 있으면 바로 읽힌다.

### `defaultdict` — 키가 없을 때 자동으로 만든다

```python
from collections import defaultdict

self.edge_shells: dict[Edge, list[int]] = defaultdict(list)
for si, sh in enumerate(self.shells):
    for e in sh.edges:
        self.edge_shells[e].append(si)     # 키가 없어도 알아서 빈 리스트 생성
```

일반 `dict` 로 하면 이렇게 써야 한다.

```python
if e not in self.edge_shells:
    self.edge_shells[e] = []
self.edge_shells[e].append(si)
```

`defaultdict(list)` 는 **"없는 키를 읽으면 `list()` 를 호출해 넣어준다"** 는 뜻이다.
`defaultdict(int)` 면 0 으로 시작하는 카운터가 된다.

### 컴프리헨션 (comprehension)

```python
TYPE_INDEX = {t: i for i, t in enumerate(ELEM_TYPES)}
```

`for` 문으로 풀면 이렇다.

```python
TYPE_INDEX = {}
for i, t in enumerate(ELEM_TYPES):
    TYPE_INDEX[t] = i
```

- 리스트: `[f(x) for x in xs]`
- 딕셔너리: `{k: v for ...}`
- 집합: `{f(x) for x in xs}`
- 조건: `[x for x in xs if x > 0]`

**3줄 넘게 복잡해지면 그냥 for 문으로 쓰는 게 낫다.** 컴프리헨션은 짧을 때만 읽기 쉽다.

### 직접 해보기
`meshrep.py` 의 `node_shells`, `edge_lines`, `node_lines` 가 각각 무엇을 키로, 무엇을
값으로 담는지 적어보라. 그리고 왜 전부 `defaultdict` 인지 설명해보라.

## 4. 클래스를 언제 쓰는가 — 이 프로젝트의 네 가지 패턴

**"클래스를 써야 하나 함수면 되나"** 는 늘 헷갈린다. 이 프로젝트에 네 가지 경우가
전부 들어 있으니 비교해 보면 기준이 생긴다.

### 패턴 ① `@dataclass` — 값을 담기만 하는 그릇

```python
@dataclass
class RawMesh:
    """.bdf + .json 을 읽은 그대로 담는 컨테이너."""

    name: str
    coords: dict[int, tuple[float, float, float]]
    shells: list[tuple[int, str, list[int]]]
    lines: list[tuple[int, str, tuple[int, int]]]
    ext: dict[int, bool]
```

`@dataclass` 데코레이터를 붙이면 파이썬이 **자동으로 만들어 준다**:

- `__init__` — `RawMesh(name=..., coords=..., ...)` 로 생성
- `__repr__` — `print(raw)` 했을 때 보기 좋은 출력
- `__eq__` — `raw1 == raw2` 비교

직접 쓰면 이렇게 길어진다.

```python
class RawMesh:
    def __init__(self, name, coords, shells, lines, ext):
        self.name = name
        self.coords = coords
        self.shells = shells
        self.lines = lines
        self.ext = ext
    def __repr__(self):
        return f"RawMesh(name={self.name!r}, ...)"
```

**언제 쓰나**: 관련된 값 여러 개를 묶어 다닐 때. 튜플로 넘기면 `result[2]` 가 뭔지
매번 세어봐야 하지만, dataclass 면 `raw.shells` 라고 읽힌다.

### 패턴 ② `@dataclass(frozen=True)` — 바뀌면 안 되는 값

```python
@dataclass(frozen=True)
class FeatureSpec:
    """이름과 종류가 짝지어진 피처 벡터의 스키마."""

    names: tuple[str, ...]
    kinds: tuple[FeatureKind, ...]

    def __post_init__(self) -> None:
        if len(self.names) != len(self.kinds):
            raise ValueError(f"names({len(self.names)}) 와 kinds({len(self.kinds)}) 길이가 다름")
        bad = set(self.kinds) - {"binary", "linear", "log"}
        if bad:
            raise ValueError(f"알 수 없는 kind: {bad}")
```

`frozen=True` 면 **만든 뒤 수정할 수 없다.** `spec.names = (...)` 하면 에러가 난다.

**왜 막았나**: 피처 스펙은 모델 구조와 정규화 통계가 전부 의존하는 값이다. 실행 중에
누가 바꾸면 조용히 어긋난다. **바뀌면 안 되는 것은 문법으로 막는다.**

`__post_init__` 은 **dataclass 전용 훅**이다. 자동 생성된 `__init__` 이 끝난 직후
불린다. 여기서 검증한다 — 이름과 종류 개수가 다르면 그 자리에서 터뜨린다. 안 그러면
한참 뒤 정규화에서 이상한 에러가 난다.

> `set(self.kinds) - {"binary", "linear", "log"}` — 집합 뺄셈이다. 허용된 것 외에
> 뭐가 들어왔는지 한 줄로 찾아낸다.

### 패턴 ③ 일반 클래스 — 상태 + 계산

```python
class MeshRep:
    """메쉬 패치 하나의 기하 + 위상 + 외부연결 정보."""

    def __init__(self, raw: RawMesh):
        self.raw = raw
        self.name = raw.name
        self.node_ids: list[int] = raw.node_ids
        self.node_index: dict[int, int] = {n: i for i, n in enumerate(self.node_ids)}
        ...
        self.edge_shells: dict[Edge, list[int]] = defaultdict(list)
        for si, sh in enumerate(self.shells):
            for e in sh.edges:
                self.edge_shells[e].append(si)
```

`@dataclass` 가 아니라 직접 `__init__` 을 쓴 이유: **생성할 때 무거운 계산을 한다.**
연결 관계(`edge_shells` 등)를 전부 미리 만들어 둔다. dataclass 는 "받은 값을 넣기만"
하는 용도라 맞지 않는다.

- `self` — 인스턴스 자기 자신. 메서드의 **첫 인자로 반드시 받는다**(자동으로 안 붙는다).
- `self.x = ...` — 인스턴스에 값을 붙인다. `__init__` 밖에서 새 속성을 만들 수도 있지만,
  **전부 `__init__` 에서 만드는 게 읽기 좋다.**
- `self.node_ids: list[int] = ...` — 속성에도 타입 힌트를 붙일 수 있다.

**왜 클래스로 묶었나**: `edge_shells`, `node_shells`, `shells`, `lines` 는 전부 같은
메쉬에 대한 것이고 **항상 같이 다닌다.** 함수 7개가 이 값들을 서로 주고받으면 인자가
폭발한다. 하나로 묶어 `rep.edge_shells` 로 꺼내 쓰는 게 낫다.

### 패턴 ④ 상속 — `nn.Module`

```python
class AttnPool(nn.Module):
    """어텐션 pooling. 게이트값(alpha)을 함께 반환해 요소 지목에 쓴다."""

    def __init__(self, dim: int):
        super().__init__()                     # 부모 초기화를 반드시 먼저
        self.gate = nn.Sequential(
            nn.Linear(dim, dim // 2), nn.ReLU(), nn.Linear(dim // 2, 1)
        )

    def forward(self, x, batch, n_graph):
        score = self.gate(x).squeeze(-1)
        alpha = softmax(score, batch, num_nodes=x.size(0))
        out = scatter(alpha.unsqueeze(-1) * x, batch, dim=0, dim_size=n_graph, reduce="sum")
        return out, alpha
```

- `class AttnPool(nn.Module)` — 괄호 안이 **부모 클래스**. nn.Module 의 기능을 물려받는다.
- `super().__init__()` — **빼먹으면 안 된다.** PyTorch 가 파라미터를 추적하는 장치가
  여기서 준비된다. 안 하면 `model.parameters()` 가 비어서 학습이 안 되는데,
  **에러도 안 난다.**
- `forward` — 이름이 정해져 있다. `self.gate(x)` 처럼 **객체를 함수처럼 호출**하면
  내부적으로 `forward` 가 불린다(`__call__` 이 그렇게 구현되어 있다).

### 그리고 — 클래스를 **쓰지 않은** 곳

`features.py` 에는 클래스가 거의 없다. 전부 이런 함수들이다.

```python
def shell_quality(P: np.ndarray) -> ShellQuality: ...
def interior_angles(P: np.ndarray) -> np.ndarray: ...
def is_bad_shell(q: ShellQuality) -> bool: ...
```

**왜 함수로 뒀나**: 이들은 **상태가 없다.** 좌표 배열을 받아 숫자를 내놓을 뿐이고,
같은 입력이면 항상 같은 출력이다(순수 함수). 이런 걸 클래스로 감싸면 테스트만 어려워진다.

> **판단 기준**
> - 값만 묶는다 → `@dataclass`
> - 바뀌면 안 된다 → `@dataclass(frozen=True)`
> - 만들 때 계산하고 그 결과를 계속 쓴다 → 일반 클래스
> - 프레임워크가 요구한다 → 상속
> - **상태가 없다 → 그냥 함수** (제일 흔한 정답)

### 직접 해보기
`src/dataset.py` 의 `NormalizerSet` 이 왜 dataclass 가 아니라 일반 클래스인지,
`state_dict()` / `from_state_dict()` 가 왜 필요한지 설명해보라.

## 5. 매직 메서드 — `__이름__`

앞뒤에 밑줄 두 개가 붙은 메서드는 **파이썬 문법과 연결된 특별한 이름**이다.
직접 부르지 않고, 특정 문법을 쓰면 파이썬이 대신 불러준다.

```python
    def __len__(self) -> int:
        return len(self.names)

    def index(self, name: str) -> int:
        return self.names.index(name)
```

| 매직 메서드 | 이걸 쓰면 불린다 | 이 프로젝트의 예 |
|---|---|---|
| `__init__` | `MeshRep(raw)` | 거의 모든 클래스 |
| `__len__` | `len(spec)` | `FeatureSpec` |
| `__repr__` | `print(obj)` | dataclass 가 자동 생성 |
| `__eq__` | `a == b` | dataclass 가 자동 생성 |
| `__post_init__` | dataclass 생성 직후 | `FeatureSpec` 검증 |
| `__call__` | `obj(x)` | `nn.Module` 이 `forward` 로 연결 |

`__len__` 을 정의한 덕에 `len(NODE_SPEC)` 으로 피처 개수를 얻는다.
`NODE_SPEC.count` 같은 걸 따로 만들지 않아도 된다 — **파이썬 기본 문법에 얹는 것**이
읽기 좋기 때문이다.

## 6. `@property` — 메서드를 속성처럼

```python
@dataclass
class RawMesh:
    coords: dict[int, tuple[float, float, float]]

    @property
    def node_ids(self) -> list[int]:
        """정렬된 절점 id 목록. 그래프 노드 순서의 기준."""
        return sorted(self.coords)

    @property
    def points(self) -> np.ndarray:
        """(n_node, 3) 좌표 배열. 행 순서는 ``node_ids``."""
        return np.array([self.coords[n] for n in self.node_ids], dtype=float)
```

`raw.node_ids` 로 쓴다. **괄호가 없다.** 함수인데 속성처럼 보인다.

**왜 이렇게 하나**: `node_ids` 는 `coords` 에서 **유도되는 값**이다. 따로 저장해 두면
`coords` 가 바뀔 때 둘이 어긋난다(동기화 문제). property 로 두면 **항상 그 자리에서
계산**하므로 어긋날 수 없다.

**주의**: 호출할 때마다 계산한다. `points` 는 배열을 새로 만드니 반복문 안에서 쓰면
느리다. 그래서 `MeshRep.__init__` 은 `self.points = raw.points` 로 **한 번만 받아 둔다.**

> 비싼 계산을 한 번만 하고 싶으면 `functools.cached_property` 를 쓴다.
> 이 프로젝트는 `__init__` 에서 미리 계산하는 쪽을 택했다.

## 7. 데코레이터 — `@` 가 하는 일

데코레이터는 **함수를 받아 함수를 돌려주는 함수**다. `@` 는 문법 설탕이다.

```python
@dataclass
class RawMesh: ...
```

이건 사실상 이것과 같다.

```python
class RawMesh: ...
RawMesh = dataclass(RawMesh)
```

### 이 프로젝트에서 쓰는 데코레이터

| 데코레이터 | 하는 일 |
|---|---|
| `@dataclass` | `__init__` 등을 자동 생성 |
| `@property` | 메서드를 속성처럼 |
| `@staticmethod` | `self` 없이 쓰는 메서드 |
| `@st.cache_data` | Streamlit — 결과를 캐시 |
| `@st.cache_resource` | Streamlit — 무거운 객체를 캐시 |

### `@staticmethod` — 클래스에 속하지만 self 를 안 쓴다

```python
    @staticmethod
    def of(*pairs: tuple[str, FeatureKind]) -> "FeatureSpec":
        """``FeatureSpec.of(("area", "log"), ("skew", "linear"), ...)``"""
        return FeatureSpec(tuple(p[0] for p in pairs), tuple(p[1] for p in pairs))
```

`FeatureSpec.of(...)` 로 부른다. 인스턴스가 없어도 된다.

**왜 만들었나**: 원래 생성자는 `FeatureSpec(("area","skew"), ("log","linear"))` 처럼
**이름 목록과 종류 목록을 따로** 받는다. 피처가 47개면 두 목록을 나란히 유지해야 해서
틀리기 쉽다. `of` 는 **짝을 지어** 받으므로 눈으로 대조된다.

```python
NODE_SPEC = FeatureSpec.of(
    ("is_quad4", "binary"),
    ("ext_frac", "linear"),
    ("s_area", "log"),
    ...
)
```

> 반환 타입이 `"FeatureSpec"` 처럼 **문자열**인 것에 주목. 클래스 정의가 아직 안 끝난
> 시점이라 이름을 직접 쓸 수 없다. `from __future__ import annotations` 가 있으면
> 따옴표 없이 써도 된다.

### `@st.cache_data` 와 `@st.cache_resource` — 그리고 그 함정

```python
@st.cache_data
def load_predictions(run_dir: str) -> pd.DataFrame: ...

@st.cache_resource(show_spinner=False)
def get_full_model(run_dir: str, device_str: str): ...
```

Streamlit 은 사용자가 버튼을 누를 때마다 **스크립트 전체를 처음부터 다시 실행**한다.
캐시가 없으면 매번 모델을 다시 읽는다.

- `cache_data` — **데이터**용. 반환값을 복사해서 준다(수정해도 캐시가 안 망가짐)
- `cache_resource` — **객체**용. 같은 객체를 그대로 준다(모델처럼 복사하면 안 되는 것)

**함정**: 캐시는 **인자 값으로만** 구분한다. 파일이 바뀌어도 인자가 같으면 옛 결과를
준다. 이 프로젝트에서 실제로 겪었다 — `predictions.csv` 를 새로 만들었는데 앱이 계속
"파일 없음"이라고 했다. **서버를 재시작해야 했다.**

## 8. 타입 힌트 문법 총정리

```python
def discover_pairs(fe_dir: str) -> tuple[dict[str, tuple[str, str]], list[str], list[str]]:
def load_run_metrics(run_dir: str) -> dict | None:
def pick_by_label(names: list[str], key: str, title: str) -> str | None:

```

| 표기 | 뜻 |
|---|---|
| `str`, `int`, `float`, `bool` | 기본 타입 |
| `list[str]` | 문자열 리스트 |
| `dict[int, bool]` | 키가 int, 값이 bool |
| `tuple[str, str]` | **정확히 2개**, 각각 str |
| `tuple[str, ...]` | str 이 **몇 개든** |
| `dict \| None` | dict 이거나 None (옛 표기: `Optional[dict]`) |
| `"FeatureSpec"` | 아직 정의 안 된 이름 (문자열로) |

**파이썬은 타입 힌트를 검사하지 않는다.** `def f(x: int)` 에 문자열을 넣어도 돌아간다.
그럼 왜 쓰나:

1. 에디터가 자동완성과 오류 표시를 해준다
2. **함수 시그니처만 보고 쓰는 법을 알 수 있다** — 이게 제일 크다
3. 나중에 `mypy` 같은 검사기를 붙일 수 있다

`-> tuple[dict[str, tuple[str, str]], list[str], list[str]]` 는 읽기 어렵지만,
"딕셔너리 하나와 리스트 둘을 준다"는 걸 **문서 안 읽고도** 안다.

## 9. numpy — 반복문을 쓰지 않는 사고방식

### 벡터화

```python
# 느린 방식
total = 0
for i in range(len(xs)):
    total += xs[i] ** 2

# numpy 방식
total = (xs ** 2).sum()
```

numpy 배열에 연산을 걸면 **모든 원소에 한꺼번에** 적용된다. 반복문이 C 레벨에서
돌기 때문에 수십~수백 배 빠르다.

### 이 프로젝트의 실제 예

```python
P = np.array([rep.raw.coords[n] for n in sh.nodes])   # (4, 3) 좌표 배열
```

쉘 하나의 네 꼭짓점 좌표를 `(4, 3)` 배열로 만든다. **행 = 점, 열 = x/y/z** 이다.
이 "모양(shape)"을 항상 의식해야 한다. numpy 버그의 대부분이 모양 착각에서 온다.

### 축(axis) — 제일 헷갈리는 것

```python
P.mean(axis=0)     # (3,)  열 방향 평균 = 각 좌표축의 평균 = 중심점
P.mean(axis=1)     # (4,)  행 방향 평균 = 점마다 x,y,z 평균 (의미 없음)
```

**`axis=0` 은 "0번 축을 없앤다"** 로 외우면 쉽다. `(4,3)` 에서 0번 축(4)을 없애면
`(3,)` 이 남는다.

### 불리언 마스크

```python
scale_mask = np.array([k != "binary" for k in self.kinds])   # True/False 배열
X[:, scale_mask] = ...                                        # True 인 열만 골라 변환
```

**조건에 맞는 것만 골라 한꺼번에** 처리한다. 이 프로젝트의 정규화가 이걸로 돌아간다 —
binary 피처는 건드리지 않고 나머지만 z-score 한다.

### 자주 쓰는 함수

| 함수 | 하는 일 | 이 프로젝트의 쓰임 |
|---|---|---|
| `np.array([...])` | 배열 만들기 | 좌표 모으기 |
| `np.zeros/full` | 초기화 | `np.full(len(y), np.nan)` |
| `np.concatenate` | 이어 붙이기 | fold 별 피처 쌓기 |
| `np.stack` | 새 축으로 쌓기 | 그래프 피처 모으기 |
| `np.argsort(-x)` | 큰 순서의 **인덱스** | 중요도 상위 요소 |
| `np.select` | 다중 조건 분기 | FP/FN/정답 분류 |
| `np.clip` | 범위 자르기 | 정규화 후 ±10 |
| `np.percentile` | 분위수 | 윈저화 |

### `np.select` 실제 코드

```python
df["kind"] = np.select(
    [(df["cls"] == 0) & (df["pred"] == 1),      # 조건 1
     (df["cls"] == 1) & (df["pred"] == 0),      # 조건 2
     df["cls"] == 2],                            # 조건 3
    ["FP", "FN", "분류어려움"],                   # 각각의 값
    default="정답",
)
```

if/elif/else 를 **배열 전체에 한꺼번에** 적용하는 것이다. 3960행을 반복문 없이 분류한다.

> `&` 는 `and` 가 아니다. numpy/pandas 에서는 **원소별 AND** 가 `&`, OR 가 `|` 다.
> 그리고 **괄호가 필수**다 — `df["cls"] == 0 & df["pred"] == 1` 은 연산자 우선순위
> 때문에 틀린다.

### 직접 해보기
`features.py` 의 `interior_angles` 를 읽고, 반복문 없이 네 꼭짓점의 내각을 어떻게
한꺼번에 구하는지 따라가 보라. 종이에 `(4,3)` 배열을 그려놓고 하면 쉽다.

## 12. PyTorch 문법

### `nn.Module` 의 뼈대

```python
class MeshGNN(nn.Module):
    def __init__(self, d_node, d_edge, ...):
        super().__init__()                       # 반드시 먼저
        self.node_enc = nn.Sequential(
            nn.Linear(d_node, hidden), nn.BatchNorm1d(hidden), nn.ReLU()
        )
        self.pool = AttnPool(hidden)

    def forward(self, data, return_alpha: bool = False):
        x = self.node_enc(data.x)
        ...
        return logit
```

**규칙**:
1. `super().__init__()` 을 `__init__` 맨 앞에
2. 학습할 층은 **`self.` 에 붙인다.** 그래야 PyTorch 가 파라미터로 추적한다.
   지역변수로 두면 학습이 안 되는데 **에러가 안 난다**
3. 계산은 `forward` 에 쓴다. 호출은 `model(data)` 로 한다 (`model.forward(data)` 아님)

### `nn.Sequential` — 층을 차례로

```python
nn.Sequential(nn.Linear(dim, dim // 2), nn.ReLU(), nn.Linear(dim // 2, 1))
```

입력이 Linear → ReLU → Linear 순서로 통과한다. `mlp()` 함수가 이걸 자동으로 만든다.

### 자주 쓰는 텐서 연산

```python
score = self.gate(x).squeeze(-1)       # (N, 1) -> (N,)   크기 1인 축 제거
alpha.unsqueeze(-1)                     # (N,) -> (N, 1)   축 추가
x.size(0)                               # 첫 번째 차원 크기
torch.cat([a, b], dim=1)                # 이어 붙이기
loss.detach().item()                    # 텐서 -> 파이썬 float
```

> `.item()` 전에 `.detach()` 를 붙이는 이유: 기울기 그래프에서 떼어낸다. 안 하면
> 경고가 나거나 메모리가 샌다.

### 장치(device)

```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = build_model(...).to(device)
data = data.to(device)
```

**모델과 데이터가 같은 장치에 있어야** 한다. 다르면 런타임 에러가 난다.

### 저장과 복원

```python
ckpt = {
    "model_state": best_state,
    "normalizer": norm.state_dict(),
    "args": vars(args),
    "platt": [a, b],
}
torch.save(ckpt, path)
```

**가중치만 저장하지 않는다.** 정규화 통계와 설정도 같이 넣는다. 안 그러면 나중에
같은 기준으로 피처를 변환할 수 없다 — 그리고 그건 **에러 없이 조용히 틀린다.**

> `vars(args)` — argparse 의 Namespace 객체를 딕셔너리로 바꾼다. 반대는
> `SimpleNamespace(**d)`.

## 13. PyTorch Geometric

### `Data` — 그래프 하나

```python
Data(
    x=x,                    # (n_node, d_node)  노드 피처
    edge_index=edge_index,  # (2, n_edge)       누가 누구와 연결됐나
    edge_attr=ea,           # (n_edge, d_edge)  엣지 피처
    y=torch.tensor([float(y)]),
    name=name,              # 아무 이름이나 추가로 붙일 수 있다
)
```

`edge_index` 가 핵심이다. `edge_index[0]` 은 출발 노드, `edge_index[1]` 은 도착 노드.
무방향 관계는 **양쪽 방향을 둘 다** 넣어야 한다(그래서 엣지 수가 2배).

### 배치 — 그래프 여러 개를 하나로

PyG 는 그래프 여러 개를 **하나의 큰 그래프**로 합쳐 처리한다. `data.batch` 가
"각 노드가 몇 번째 그래프 소속인지"를 알려준다.

```python
alpha = softmax(score, batch, num_nodes=x.size(0))   # 그래프별로 따로 softmax
out = scatter(alpha.unsqueeze(-1) * x, batch, dim=0, dim_size=n_graph, reduce="sum")
```

- `scatter(..., batch, reduce="sum")` — **그래프별로 묶어서 합산**
- `softmax(score, batch)` — 그래프 안에서만 확률 합이 1

이 두 함수가 "그래프마다 요소 수가 다른" 문제를 해결한다.

## 14. 예외와 검증 — 조용히 틀리지 않게

### 커스텀 예외

```python
class BdfFormatError(ValueError):
    """.bdf 가 이 데이터셋의 가정을 벗어날 때."""
```

`ValueError` 를 상속한 **이름만 있는 클래스**다. 본문은 docstring 하나뿐이고 `pass`
대신 docstring 이 그 자리를 채운다.

**왜 만드나**: 호출하는 쪽이 `except BdfFormatError:` 로 **이 에러만** 잡을 수 있다.
그냥 `ValueError` 를 던지면 다른 원인의 ValueError 와 구분이 안 된다.

### `assert` 와 `raise` 의 차이

```python
assert not np.isnan(oof).any(), "out-of-fold 예측이 비어 있는 샘플이 있음"
raise ValueError(f"{path}: 필요한 컬럼을 못 찾음 (컬럼: {cols})")
```

| | 용도 | 주의 |
|---|---|---|
| `assert` | **내가 짠 코드의 논리** 검증 | `python -O` 로 실행하면 **전부 사라진다** |
| `raise` | 입력·환경 문제 | 항상 동작 |

**사용자 입력 검증에 assert 를 쓰면 안 된다.** 최적화 모드에서 검증이 통째로 없어진다.

### 에러 메시지에 값을 넣는다

```python
raise ValueError(f"names({len(self.names)}) 와 kinds({len(self.kinds)}) 길이가 다름")
```

"길이가 다름"만 쓰면 디버깅할 때 다시 찍어봐야 한다. **실제 숫자를 넣으면** 메시지만
보고 원인을 안다.

## 15. 자주 쓰는 관용구

```python
for i, s in enumerate(samples, start=1):        # 번호를 같이
for d, n in zip(disp, names):                   # 두 목록을 나란히
sorted(paired)                                   # 정렬된 새 목록
sorted(rows, key=lambda r: -r["prob"])           # 기준을 정해 정렬 (내림차순)
any("이름" in c for c in cells)                  # 하나라도 참이면
all(m in c for m in musts)                       # 전부 참이면
x = a if cond else b                             # 삼항 연산자
f"{p:.4f}"                                       # 소수점 4자리
f"{acc:.1%}"                                     # 퍼센트 (0.9364 -> 93.6%)
f"{n:,}"                                         # 천 단위 쉼표 (231,170)
f"{name:12s}"                                    # 12칸 왼쪽 정렬
f"{val!r}"                                       # repr() 로 (따옴표 포함)
```

### f-string 포맷이 왜 중요한가

출력을 눈으로 확인하는 일이 많은 프로젝트다. 자릿수를 맞춰 찍으면 **이상한 값이
바로 눈에 띈다.**

```python
print(f"  {k:8s} {fold_mean[k]:.4f} ± {fold_std[k]:.4f}       {overall[k]:.4f}")
```

### 딕셔너리로 분기 — if 사슬 대신

```python
want = {"FP (정상을 비정상으로 오판)": ["FP"],
        "FN (비정상을 정상으로 오판)": ["FN"],
        "둘 다": ["FP", "FN"]}[kind]
```

`if/elif/elif` 를 딕셔너리 조회 한 번으로 바꾼다. 선택지가 많을수록 읽기 좋다.

### `getattr` 로 하위 호환

```python
separate_encoder = getattr(args, "separate_encoder", False)
```

"`args` 에 그 속성이 있으면 쓰고, 없으면 False". **예전에 저장한 체크포인트에는 그
옵션이 없기 때문**이다. 이게 없으면 옛 모델을 못 읽는다.

## 16. "안 보고 짜기" 훈련 과정

읽기만 해서는 안 된다. 아래 순서로 **직접 쳐보는 것**이 목표다.
각 단계는 빈 파일에서 시작한다. 막히면 원본을 보되, 본 뒤에는 **닫고 다시 쳐라.**

### 1주차 — 파이썬 기본기

1. `features.py` 의 `interior_angles` 를 아무것도 안 보고 다시 짜라.
   입력 `(4,3)` 배열, 출력 `(4,)` 각도 배열. numpy 만 쓴다.
2. `Edge = frozenset` 을 쓰지 **않고** 같은 일을 하는 코드를 짜보라.
   왜 frozenset 이 나은지 몸으로 알게 된다.
3. `RawMesh` 를 `@dataclass` 없이 손으로 써보라. 그다음 dataclass 로 바꿔보라.

### 2주차 — 자료구조와 클래스

4. 빈 파일에서 `MeshRep` 의 `edge_shells` 생성 부분만 다시 짜라.
   쉘 목록을 받아 "변 → 쉘 목록" 딕셔너리를 만든다.
5. 거기서 경계변/정상변/비정상변 개수를 세는 함수를 추가하라.
6. `FeatureSpec` 을 다시 짜라. `frozen=True`, `__post_init__` 검증, `of` 까지.

### 3주차 — 파이프라인

7. `bdf_io.read_bdf` 를 다시 짜라. 파일 한 개만 제대로 읽으면 된다.
8. 피처 5개짜리 작은 `FeatureSpec` 과 `Normalizer` 를 짜라.
   학습 몫에서만 통계를 적합하도록 **반드시** 그렇게 짜라.
9. 메쉬 하나를 `(x, edge_index, edge_attr)` 로 바꾸는 함수를 짜라.

### 4주차 — 모델과 학습

10. `AttnPool` 을 다시 짜라. `softmax` 와 `scatter` 가 왜 `batch` 를 받는지 설명하라.
11. 2층짜리 아주 작은 GNN 을 짜고, 메쉬 10개로 과적합시켜 보라.
    **학습 데이터에서 loss 가 0 에 가까워지면** 연결이 제대로 된 것이다
    (이건 디버깅 기법이다. 실제 학습 목표가 아니다).
12. 학습/검증 분리와 조기종료를 넣어라. 검증 성능이 꺾이는 지점을 눈으로 확인하라.

### 마지막 점검 — 이걸 설명할 수 있으면 된 것이다

- 왜 노드를 절점이 아니라 요소로 뒀는가?
- 왜 좌표 절대값을 피처에 넣지 않는가?
- 정규화 통계를 전체 데이터로 구하면 무엇이 잘못되는가?
- `frozen=True` 를 붙인 이유는?
- `super().__init__()` 을 빠뜨리면 무슨 일이 일어나는가?
- 학습 데이터 정확도가 100%면 왜 문제인가?
- 캐시에 라벨을 담으면 안 되는 이유는?

## 부록. 파일을 짜는 순서 (.py 단위)

단계가 아니라 **파일 하나하나의 순서**로 본 것이다. 순서의 근거는 취향이 아니라
**import 의존 관계**다 — A 가 B 를 import 하면 B 를 먼저 짜야 한다. 실제 의존 관계를
뽑으면 7층으로 갈라지고 순환은 없다.

```
0층  paths, bdf_io, labels, features, featspec, graph_base, models, fasoo_drm
1층  meshrep(<-bdf_io,features)  data_index(<-bdf_io,labels,paths)
2층  graph_elem, graph_node(<-featspec,features,graph_base,meshrep)  baseline  check_parsing
3층  graphs(<-graph_elem,graph_node)
4층  dataset(<-graphs,featspec,data_index)
5층  train, explain(<-dataset,models)
6층  app, predict_all, compare
```

의존 관계는 "이것보다 늦게"만 정해준다. 그 안에서는 **검증 가능한 것부터, 위험한 것부터**
짠다. 그래서 실제 작성 순서는 이렇게 된다.

| # | 파일 | 왜 이때 | 다음으로 넘어가도 되는 기준 |
|---|---|---|---|
| 1 | `paths.py` | 3줄짜리지만 제일 먼저. 경로가 흩어지면 나중에 전부 뒤져야 한다 | 상수 3~4개 |
| 2 | `bdf_io.py` | 모든 것이 이 위에 쌓인다. 가정을 `assert` 로 박는다 | 파일 하나가 파싱된다 |
| 3 | `labels.py` | 엑셀 헤더 위치를 스캔해서 찾는다 | 라벨 분포가 출력된다 |
| 4 | `data_index.py` | "무엇을 학습에 쓸지"를 한 곳에서 정한다 | 학습 대상 개수가 나온다 |
| 5 | **`check_parsing.py`** | **모델보다 먼저.** 전 파일 검증 + 회귀 테스트 | 4000개가 예외 없이 통과 |

| 10 | `graph_base.py` | `GraphArrays` 자료구조 하나뿐 | 필드가 정해졌다 |
| 11 | `graph_elem.py` | 여기가 제일 중요하고 제일 오래 걸린다 | 3D 로 그려서 눈으로 봤다 |
| 12 | `graphs.py` | 빌더를 고르는 얇은 층 | — |
| 13 | `dataset.py` | 캐시 + fold 단위 정규화 + PyG 변환 | 정규화가 학습 몫에서만 적합된다 |
| 14 | `models.py` | 단순한 것부터. 어텐션 풀링을 넣는다 | 메쉬 10개에 과적합된다 |
| 15 | `train.py` | 학습 루프와 평가 프로토콜 | 기준선을 넘었다 |
| 16 | `compare.py` | 실행들을 한 표로 | — |

### 순서에서 꼭 지켜야 할 세 가지

**① `check_parsing.py`(5번)를 모델보다 먼저 만든다.**
파싱이 틀린 채로 모델을 짜면, 성능이 안 나올 때 원인이 모델인지 데이터인지 알 수 없다.
회귀 테스트 한 줄(`0001 = 절점 55 / CQUAD4 42 / CTRIA3 1 / CBAR 29 / CBEAM 9`)이
이후 모든 수정에서 안전망이 된다.

**② `baseline.py`(8번)를 GNN 보다 먼저 만든다.**
반나절이면 짜는데, 이게 없으면 나중에 "AUC 0.98" 이 좋은 숫자인지 말할 수 없다.

**③ `graph_node.py`(18번)는 일부러 늦게 만든다.**
두 표현을 비교하는 건 중요하지만, **처음부터 둘 다 만들면 둘 다 어설프게 된다.**
요소 기반으로 끝까지 가서 전체 파이프라인을 완성한 뒤, 비교군으로 추가하는 편이 낫다.

### 각 파일의 분량 감각

실제 이 프로젝트의 크기다. 처음 짤 때 "이 정도면 되는구나"의 기준으로 삼으면 된다.
